# Audit UX « Simplicité — Praticité — Fiabilité » — Fullstack Produits

> Audit statique réalisé le 2026-11-03. Périmètre : parcours utilisateurs du frontend
> React (`frontend/frontend/src/`) + enchaînements backend (`backend/api/`).
> Aucune modification de code — rapport uniquement.
>
> **Constat central** : la fiabilité technique est forte (idempotence, verrous,
> audit, autosave, PDA offline) et le clavier est bien pensé en facturation/commandes.
> Le maillon faible est la **simplicité** : cascades de modales, sudo omniprésent
> sur les actions répétitives, et parcours éclatés sur plusieurs écrans. Le levier
> principal n'est pas d'ajouter des features mais de **réduire le nombre de modales
> et de mots de passe sur les actions quotidiennes**.

---

## 1. Synthèse

| Axe | État | Constat |
|---|---|---|
| Fiabilité | ✅ Fort | Idempotence anti-double-soumission, verrous optimistes/pessimistes, autosave granulaire, audit complet, PDA offline, garde-fous backend sérieux |
| Praticité | 🟡 Correct | Scan auto + DataMatrix, raccourcis F1-F10, auto-focus systématique, Ctrl+K omnisearch (78 pages), hubs Stock/Rapports |
| Simplicité | 🔴 Faible | Jusqu'à 5 modales en cascade, sudo à chaque vente, retours éclatés sur 3 écrans, réglages morts, hints clavier non implémentés |

| # | Processus | Étapes réelles | Friction dominante |
|---|---|---|---|
| 1 | Vente bout-en-bout (vendeur + caissier) | ~9-11 interactions + 1 mot de passe, 2 écrans | Sudo à **chaque** vente |
| 2 | Clôture de commande | 4-5 modales en cascade | 3 confirms + sudo ; warning non actionnable |
| 3 | Ajustement de stock | 3 modales (ajustement → mot de passe → toast) | Pas de delta ni de bulk |
| 4 | Saisie lignes de commande | ~110-130 interactions / 10 lignes | 8 champs traversés par ligne |
| 5 | Avoir fournisseur | ~4 écrans, 2 passages sudo | Type d'avoir jamais proposé |
| 6 | Ouverture / clôture de caisse | 3-4 clics | Pas de billetage ni d'impression à la fermeture |
| 7 | Import produits | mot de passe **avant** l'écran | Ordre des modales inversé |
| 8 | Retours | 3 écrans différents | Annulation / avoir client / avoir fournisseur éclatés |

## 2. Parcours « Vente en caisse »

### 2.1 Architecture : deux écrans

| Écran | Route | Rôle |
|---|---|---|
| Facturation (POS vendeur) | `/app/facturation` | Panier, envoi en caisse — n'encaisse ni n'imprime pas |
| Caisse centralisée | `/app/caisse-centralisee` | Encaissement des factures en attente, sessions, coupons |

⚠️ Le réglage `centralized_cash_register` existe dans `invoice-settings/` et l'UI
(`PrintingTab.tsx:198-205`) mais **n'est pas lu** : `useMultiCaisse.ts:25` force
`true` en dur. Le mode « vendeur encaisse au comptoir » est impossible.

### 2.2 Vendeur (~4-5 interactions + mot de passe)

1. Scan code-barres → ajout auto (match CIP exact) ou saisie ≥3 car. → `↓` → `Enter`.
   ⚠️ `Enter` seule ne sélectionne **pas** le 1er résultat (`useFacturationSearch.ts:144-150`).
   Interruptions possibles : ordonnance, alerte comptoir, stock ≤0, interactions.
2. Quantité auto-focalisée ; `N*` en recherche pour saisie rapide.
3. `F9` Payer → refresh stock → éventuelle `StockResolutionModal` (rupture).
4. `PaymentModal` (montant en lecture seule en mode centralisé → quasi une simple
   confirmation) → `Enter`.
5. **Sudo `can_validate_sales` obligatoire à chaque vente** (`useFacturationState.ts:449-463`)
   — mot de passe complet, jamais mis en cache entre ventes.
6. Toast « envoyé en caisse », panier reset, focus recherche. **Aucun ticket au POS.**

### 2.3 Caissier (~5 interactions)

Ouvrir caisse (3 clics, pas d'auto-ouverture) → sélection facture (j/k, 1-9) →
Encaisser → modale paiement (`Enter`×2 pour espèces exact, rendu monnaie géant) →
aperçu ticket auto → `Enter` imprime (QZ Tray + fallback HTML) → fermer.

### 2.4 Ouverture / clôture de caisse

- Ouverture caissier : 3 clics (`OpenCashSessionModal` — l'`autoOpen` existe
  `:54-56` mais n'est jamais activé). Vendeur : modale bloquante si aucun poste (2 clics).
- **Deux mécanismes de clôture coexistent** : fermeture de poste (caisse, sans
  billetage ni bouton imprimer — `ClosingReportModal.tsx:41-50`) et clôture
  comptable (`/app/journal-caisse`, avec billetage + impression auto) — le comptage
  physique n'existe que sur la 2ᵉ page.

### 2.5 Frictions vente

1. **Sudo à chaque vente** — friction n°1 du flux quotidien.
2. Double modale séquentielle PaymentModal → SudoModal pour une action.
3. Process sur 2 écrans / 2 acteurs ; mono-opérateur pénalisé (réglage mort).
4. Ticket jamais imprimé automatiquement.
5. `Enter` ≠ 1er résultat de recherche.
6. Vérif stock faite 2× au checkout (`bulk_refresh` à F9 **et** dans `completeSale`).
7. Cas dégradés : jusqu'à 5 modales (rupture → sudo force → paiement → sudo → nom client A4).
8. Rendu monnaie absent côté vendeur ; pas de touche dédiée par mode de paiement en caisse.

## 3. Parcours « Commande fournisseur »

### 3.1 Création + saisie

Chemin minimal clavier : 1 clic création + par ligne (recherche → Enter → qté →
**~8 Enter de traversée** : qté→UG→prix→TVA→marge→PV→lot→DLC → retour recherche).
≈ 110-130 interactions pour 10 lignes. Réductible via : import CSV, suggestions,
création depuis alertes/cadencier, scan DataMatrix (lot+DLC), duplication de ligne.
Prix/TVA/marge/PV pré-remplis ; autosave brouillon (10 s + 120 s).

### 3.2 Clôture = réception (pas d'écart « commandé/reçu »)

Enchaînement : warning péremptions manquantes → warning vente à perte → confirm
générique → **modale sudo** (`useCommandeHandlers.ts:71-158`) = 4-5 modales.
Le warning péremption n'est **pas actionnable** (« vérifier » = abandonner).
Backend solide : `select_for_update`, idempotency-key, lots `CMD{id}-{pos:02d}`,
PMP, paiement auto, `closed_by` = validateur sudo réel.

⚠️ **Asymétrie** : « annuler une réception » = sudo **sans confirmation préalable**
(`useCommandeHandlers.ts:189-202`) — plus destructeur que clôturer, moins gardé.

### 3.3 Frictions commandes

1. Cascade de modales à la clôture (§3.2).
2. 8 champs traversés par ligne — pas de mode « réception rapide » (qté+lot+DLC).
3. **Hints F2 / F4 / Ctrl+A affichés mais non implémentés** (`CommandeForm.tsx:228-233`)
   — UI mensongère ; seul Shift+Enter fonctionne.
4. Suppression de ligne = 2 clics (poubelle → confirm).
5. Pas de saisie en masse hors CSV (pas de collage, pas d'« appliquer à la sélection »).
6. Transfert de lignes : pas de toast, nouvelle commande non ouverte, suppression
   source dépendante de l'autosave, N POST unitaires (`TransferCommandeModal.tsx:118-164`).
7. Pas d'écart de réception tracé (« commandé 10 / reçu 8 » = modifier la qté, sans trace).
8. Sauvegarde explicite → retour forcé à la liste (`useCommandeActions.ts:150`).
9. Sélecteur fournisseur natif sans recherche ; export = clic mort en CREATE
   (`ExportCommandeModal.tsx:151`) ; header très dense.
10. Pas de statut « envoyée » ni télétransmission (`has_teletransmission` existe,
    `orders.py:494`, inutilisé) — envoi = export CSV.

## 4. Parcours « Inventaire / Stock / Produits »

### 4.1 Inventaire web (~6 clics création + ~2-4 actions/ligne + sudo)

Liste (2 clics sidebar) → `InventaireCreateModal` assistant 2 étapes
(Vérifier/Saisie + GLOBAL/RAYON/RESERVE) → éditeur (recherche F3, modale lot
obligatoire par produit à lots, autosave 1,5 s / bulk 5 s, import CSV) →
Valider → modale sudo `can_adjust_stock`. Backend : garde-fous, optimistic
locking, `StockAdjustment` + `MouvementStock`.

### 4.2 Inventaire PDA

Login → liste EN_COURS (catalogue offline obligatoire) → création minimaliste
(réf auto, **toujours GLOBAL**, pas de pré-remplissage) → scanner (mode rapide :
scan = +1, **0 clic**) → sync bulk merge. ⚠️ Validation impossible sur PDA
(voulu : comptage/revue séparés).

### 4.3 Fiche produit

`ProduitFormModal` : ~28 champs, **1 seul écran sans onglets** (7 sections
empilées), 3 obligatoires. Recalculs coef/%marge/PV bidirectionnels (riche mais
dense). Champs payload fantômes sans UI : `fournisseur`, `description`,
`unite_mesure`, `is_perissable`, `surveillance_category`, `is_supplier_exclusive`.
Création rapide : `QuickCreateProductModal` (9 champs) depuis Commandes/Inventaire.
Import Excel : mot de passe **avant** l'écran (`ProduitShadcn.tsx:88-97`), job
async + rapport xlsx ; doc/UI de colonnes possiblement décalées.

### 4.4 Ajustement de stock

Produit → Ajuster → `StockAdjustmentModal` (lot, quantité **absolue** rayon/réserve,
motif obligatoire) → `PasswordConfirmModal` → POST. **3 modales en cascade**,
pas de delta direct, pas de bulk, `reason_detail` non exposé.

### 4.5 Avoirs / retours

- **Fournisseur** (`/app/avoirs`) : form → brouillon → valider (administratif, sans
  effet stock) → **décharger** (sudo) → clôturer par ligne. ~4 écrans, 2 passages
  sudo. ⚠️ Aucun sélecteur `type_avoir` → toujours `PERIME` (`useAvoirsStore.ts:63`)
  alors que le modèle en a 5 ; `window.confirm` natif au milieu des Dialogs.
- **Client** (`/app/avoirs-clients`) : recherche facture → lignes/lots pré-remplis
  → motif → créer (`can_create_client_credit`) → valider + choix remboursement
  (réintègre stock par lot, refuse lot périmé). Chemin retour éclaté :
  annulation facture (Ventes) ≠ note de crédit (Avoirs clients).

## 5. Frictions transverses

| Thème | Détail |
|---|---|
| Sudo omniprésent | Vente (à chaque fois), ajustement, validation inventaire, décharge avoir, annulation, sorties périmés — sécurisé mais +1 écran + frappe partout ; aucun mode « session débloquée » |
| Cascades de modales | Clôture commande (4-5), vente dégradée (5), ajustement (3), import (mot de passe avant l'écran) |
| Réglages morts | `centralized_cash_register` ignoré ; `require_validator_password` exposé mais non exploité |
| UI mensongère | Hints F2/F4/Ctrl+A sans handlers (commandes) |
| Incohérences | 4 mécanismes de confirm (window.confirm, ConfirmDialog, PasswordConfirmModal, SudoValidationModal) ; annulation réception moins gardée que clôture |
| Éclatement | Retours sur 3 écrans ; clôture caisse sur 2 pages ; encaissement séparé de la vente |

## 6. Points forts à préserver

- Scan auto-détecté (vitesse de frappe) + DataMatrix GS1 avec résolution de lot.
- Raccourcis POS complets (F1-F10, Ctrl+F/M/S, `N*`, j/k en caisse, `?` aide).
- Auto-focus systématique (recherche, quantité, valider, imprimer, mot de passe).
- Autosave brouillon commande/inventaire, panier persisté par utilisateur.
- Idempotence déterministe, verrous ligne, optimistic locking, `*_by` = validateur réel.
- Pré-remplissage intelligent (prix/TVA/marge/PV en commande ; lignes avoir client).
- PDA : mode rapide « scan = +1 », offline robuste, sync merge anti-doublon.
- Omnisearch Ctrl+K (pages + entités + actions rapides), hubs tuiles, prefetch routes.
- Aides contextuelles riches en commande (badge moins cher, historique ligne,
  repère de reprise, duplication multi-lots, fusion auto de lots).

## 7. Recommandations priorisées

### P0 — gain quotidien, risque faible

1. **Sudo vente** : mode « session débloquée N minutes » ou honorer
   `require_validator_password` (déjà dans invoice-settings) — friction n°1.
2. `Enter` = 1er résultat de recherche produit (`useFacturationSearch.ts`).
3. Regrouper les warnings de clôture commande en **1 modale actionnable**
   (lien/focus vers les lignes fautives).
4. Ajouter un confirm avant « annuler réception » (`useCommandeHandlers.ts:189`).
5. Implémenter ou retirer les hints F2/F4/Ctrl+A (`CommandeForm.tsx:228-233`).
6. Toast de succès au transfert de lignes + ouvrir la commande cible.

### P1 — simplification structurelle

7. Lire `centralized_cash_register` → mode mono-écran vendeur+encaissement
   (petites pharmacies mono-opérateur).
8. Option `auto_print_ticket` (pipeline QZ déjà en place).
9. Mode « réception rapide » commande (qté+lot+DLC) ou saisie en masse lot/DLC
   sur la sélection.
10. Sélecteur `type_avoir` dans `AvoirsForm` ; remplacer `window.confirm` par `ConfirmDialog`.
11. Billetage + bouton imprimer dans `ClosingReportModal` (fermeture de poste).
12. `autoOpen` sur `OpenCashSessionModal` à l'arrivée sur `/app/caisse-centralisee`.
13. Mutualiser `bulk_refresh` (2 appels au checkout).
14. Import produits : mot de passe après le choix du fichier, pas avant l'écran.

### P2 — dette fonctionnelle

15. Statut « envoyée » + vrai flux d'envoi/télétransmission commandes.
16. Écarts de réception tracés (« commandé/reçu »), bulk ajustement stock,
    quantités en delta dans `StockAdjustmentModal`.
17. Unifier les mécanismes de confirm ; Combobox fournisseur avec recherche ;
    corriger l'export en CREATE ; onglets ou sections repliables fiche produit.
